# vtebench — five-way comparison, 2026-04-20

> **SUPERSEDED by `throughput-2026-06-09.md`** (seven terminals, fixed
> geometry templating, plus kitty's `kitten __benchmark__`). Kept for
> history; note this run's scroll-region numbers were affected by the
> unsubstituted-geometry bugs documented there.

[`vtebench`](https://github.com/alacritty/vtebench) is the benchmark suite
maintained by the Alacritty team. It measures PTY-drain throughput — the
wall-clock time a terminal takes to accept and render a fixed payload of
escape sequences written to its TTY. It does **not** measure input latency,
frame pacing, or scroll smoothness.

> **Last verified**: 2026-05-18 against v0.2.6. Spot-checked the
> ~120 commits to `core/` and `Sources/Renderer/` since the run; none
> touched the per-byte feed / parse loop or the per-row render cache
> hot path in a way expected to shift MB/s outside benchmark noise.
> Re-run before v0.3.

Run via `scripts/bench-vte-compare.sh`. Raw per-sample data lives in
`/tmp/bb-bench/results/*.dat`; `scripts/bench-vte-summarize.py` turns those

## Methodology

- vtebench 0.3.1 (`/tmp/bb-bench/vtebench`, built with `cargo build --release`).
- Each sample is ≥1 MiB of payload (vtebench's `--min-bytes` default); the
  per-benchmark budget is `--max-secs 3 --max-samples 30`.
- The runner in each terminal first emits `\e[8;50;200t` (XTWINOPS) to
  request a 50×200 cell size, sleeps 1 s for layout, then invokes vtebench
  with `--silent` (benchmark payload goes straight to the TTY; only the
  per-benchmark timing table is written to disk as a gnuplot `.dat`).
- The stock vtebench `cursor_motion` and `light_cells` scripts resolve the
  terminal's geometry via `tput cols < $tty` / `tput lines < $tty`. When
  vtebench spawns the script via `Command::output()` there is no TTY, so
  those scripts emit zero bytes and get silently dropped. We copy the
  benchmark tree to `benchmarks-fixed/` and substitute 200×50 constants so
  every benchmark produces payload.
- Versions: Alacritty 0.17.0 (cargo-installed, release profile), Ghostty
  1.3.1, iTerm2 3.6.9, Terminal.app (Tahoe 25D2128), Blackbird Release
  build.
- Hardware: Apple Silicon, Built-in Retina Display (ProMotion 120 Hz).

## Per-terminal automation tricks

macOS terminals vary widely in how scriptable they are. The bench driver
runs entirely from Blackbird (the same instance hosting Claude Code), which
means *extended-dictionary* AppleScript to iTerm / Terminal / Ghostty is
denied (TCC Automation). Routes that actually worked:

| Terminal     | Mechanism |
|--------------|-----------|
| Terminal.app | Rename the runner to `run-terminal.command`, then `open` it — LaunchServices routes `.command` files to Terminal.app. |
| iTerm2       | `open -na iTerm --env ZDOTDIR=<dir>` — iTerm spawns `zsh -l`, zsh reads `$ZDOTDIR/.zprofile` before the interactive prompt, and our `.zprofile` execs the runner. `-n` is required so `--env` takes effect. |
| Alacritty    | `alacritty -e /bin/bash <runner>` — first-class `-e` support. |
| Blackbird    | Clone Release/Blackbird.app to `/tmp/BlackbirdBench.app`, rewrite `CFBundleIdentifier`, ad-hoc re-sign; then `open -n -F --env SHELL=<shim>`. Blackbird reads `$SHELL` from its launchd environment and execs it as the window's child process; the shim is the runner. The id rewrite is what lets `open -n` spawn a second instance alongside the user's live Blackbird. |
| Ghostty      | Clipboard paste. Ghostty's `-e`, `--command=`, and config-file `command` settings are all ignored when the app is started via `open -na Ghostty.app`: the process starts, `initial-command = true`, but no surface is ever created until a GUI event triggers it. We `pbcopy` the runner command and ask the user to paste + Enter into an open Ghostty window. |

## Caveats, not hidden

- **Window sizes differed.** Only Terminal.app honoured the `\e[8;50;200t`
  resize request and ran at 200×50. Blackbird, Alacritty, Ghostty, and
  iTerm stayed at their defaults (80×24). vtebench normalises payload to
  ≥1 MiB per sample, so MB/s remains meaningful across sizes — but the
  scroll-region benchmarks set the scroll region to rows 1–49 with
  `\e[1;49r`, which is degenerate on a 24-row window.

- **†iTerm's geomean is a 24-row artifact.** With a 1–49 scroll region on a
  24-row window, iTerm spends ≥100 s on a single sample of
  `scrolling_bottom_region`. Excluding the four scroll-region rows, iTerm's
  geomean over the remaining eight benches is ≈5 MB/s — still the
  slowest of the five, but not 1.3. The "1.3" number is honest vtebench
  output; it just isn't a claim about iTerm's real-world scroll perf.

- **vtebench ≠ the whole story.** Input latency, frame pacing, and scroll
  smoothness are not measured. Blackbird's keystroke-to-pixel latency gate
  lives in `scripts/bench-latency.sh` (CI-enforced p50 ≤ 6 ms, p99 ≤
  20 ms; see `.github/workflows/ci.yml` `latency-gate` job) — that's
  the number I actually care about when tuning render
  cost. Alacritty and Ghostty advertise GPU-accelerated rendering that
  should do well on a latency rig too; vtebench doesn't speak to that.

- **One run, one machine.** These numbers are not averaged across runs and
  there's no cross-machine variance baked in. Order-of-magnitude
  confidence only.
